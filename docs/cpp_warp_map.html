C++ 원본과 Warp 재작성이 정확히 어떻게 대응하는가

legacy/DiffMPMLib3D(C++)와 physmorph/mpm(Warp)을 커널 단위로 맞춰본 대조표. 전방 시뮬레이션은 수식 수준에서 거의 1:1이고, Warp 쪽에 네 가지 확장과 한 가지 구현 차이가 있으며, 반대로 C++ 옵티마이저에만 있는 장치 네 가지가 Warp에 없다.

근거: 양쪽 소스를 직접 읽고 대조 · 실행 확인은 hyde06

§1

전방 시뮬레이션 — 커널 단위 대조

C++는 입자 하나를 처리하는 함수 + OpenMP 루프, Warp는 @wp.kernel + wp.tid(). 스텐실·가중치·계수가 전부 같다.

§2

차이 요약

전방 시뮬레이션은 사실상 1:1이다. 보간·스텐실·C0·drag·APIC·응력·F 적분·스무딩·체적 계산이 전부 같은 식이다. kernels.py 첫 줄의 "Oracle: DiffMPMLib3D/ForwardSimulation.cpp"는 정확한 서술이다.
구분내용기본값에서
Warp 확장 ①소성 rest-state Fe=(F+dFc)(Fpl)−1Fpl=𝟙 → 차이 없음
Warp 확장 ②점성 η (객관 eta_sym / 지수 eta_mode)η=0 → 차이 없음
Warp 확장 ③v_max G2P 속도 클램프0 = off → 차이 없음
Warp 확장 ④바닥 접촉 + Coulomb 마찰, NaN 가드floor 미설정 → 차이 없음
구현 차이회전 R: 극분해(C++) vs 부호 SVD(Warp)det F>0이면 동일

즉 확장 넷은 전부 기본값에서 비활성이라, 같은 설정을 주면 두 구현은 같은 물리를 돌린다. 이것이 C++를 독립 검증용 오라클로 쓸 수 있는 근거다.

§3

반대로 — C++ 옵티마이저에만 있고 Warp에 없는 것

전방은 Warp가 더 풍부하지만, 최적화 레이어는 C++가 더 갖췄다. 아래 넷은 연구가 아니라 포팅 대상이다.

§4

Step 0 실측 — 기존 morph_mass는 실제로 뭘 내는가

같은 코드 경로에서 λ만 바꾼다: L = D_vol + λ·D_img + cohesion. λ=0이 곧 Xu et al. 목적함수, λ>0이 렌더 가이드. isosphere→bunny, 20,000 입자, K=30 프레임, arm당 6초.

렌더 가이드는 작동한다 — 기본 λ가 두세 자릿수 작았을 뿐이다. λ를 0→1000으로 올리면 chamfer 0.188→0.151, 실루엣 IoU 0.857→0.924로 둘 다 단조 개선된다. 그리고 λ=100까지는 D_vol이 나빠지지 않는다(2.23→2.09) — 3-D 충실도를 팔아 실루엣을 사는 게 아니라 양쪽이 같이 좋아진다. det F도 0.56~0.60으로 건강하다(반전 없음).
스케일이 원인이라는 증거. 최종 상태에서 Dvol ≈ 2.1, Dimg ≈ 0.024 — 약 90배 차이다. 그래서 λ=0.5에서는 렌더 항의 기여가 0.014로 사실상 0이었다. λ≈100에서 λ·Dimg ≈ 1.08이 되어 Dvol과 같은 자릿수가 되고, 바로 거기서 효과가 나타난다.

이건 §3의 λ = α·phys_norm/render_norm이 정확히 자동화하려던 것이다. 수동 λ 튜닝 대신 노름 비로 균형을 맞추면 이 스케일 문제가 구조적으로 사라진다.
측정상 주의 하나. morph_mass의 기본 promote_F=False는 매 프레임 F를 항등으로 리셋하므로 반환된 det F가 무조건 1이 되어 무의미하다. 위 표는 promote_F=True로 측정했고, 이 설정에서 D_vol 자체도 11.7 → 2.2로 크게 좋아진다(F를 프레임 간에 유지하는 편이 낫다).
